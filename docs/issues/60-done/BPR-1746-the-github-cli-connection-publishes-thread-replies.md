# BPR-1746: The GitHub CLI connection publishes thread replies

## Owner decision

2026-10-23, relayed by the coordinator, verbatim: "Oh yeah sure let gh allow
that."

[[BPR-1745]] found that `gh_cli_transport` refused `reply_review_thread`
(`addPullRequestReviewThreadReply`) for current and outdated threads alike, so
a user signed in through `gh` could not publish a reply; its live course
carried the reply's bytes over `gh` by hand. It also left `viewerCanReply` and
the pull request's lock unread, so a reply GitHub would refuse was refused only
after Publish.

## Authority widening

The CLI connection's fixed GraphQL allow-list grows by the reply write and the
read that reconciles it. Before this card it held six fixed requests for
resolution and reactions ([[BPR-1741]]) and the pending tour stop edit; now it
also holds `ReplyToThread` and `ObserveThreadComments`. Each body must equal its
compiled form byte for byte, or nothing is launched. The reply is the native
reply, inside one account lease ([[BPR-1370]]). It takes the `ObserveThread`
pre-flight, the `ObserveThreadComments` baseline, the journal admission, the
viewer and pull request observations, the write and the reconciliation. It is
witnessed: the journal marks it possibly sent before `gh` launches, so a lost
answer is settled from the thread and the reply is never written twice. Every
other GraphQL write is still refused. Recorded in
`docs/architecture/github-provider-contract.md`,
`docs/architecture/review-round-trip.md` and `src/adapters/github/AGENTS.md`.

## Design

- **Host performs** (`gh_cli_transport.cpp`). The refusal of
  `reply_review_thread` and `observe_review_thread_comments` is gone; both are
  GraphQL operations of the closed catalog, validated by
  `validate_outbound_review_mutation_request` before any launch.
- **The read.** The capability probe already introspects
  `PullRequestReviewThread` and `PullRequest`; two new schema facts,
  `reply_permission` (`viewerCanReply: Boolean!`) and `conversation_lock`
  (`locked: Boolean!`), project to read-shape flags `ReplyPermission` and
  `ConversationLock`, only with the threads. The conversation read selects
  `viewerCanReply` on each thread and `locked` on the initial page. It keeps
  them as `github_review_thread_record::ViewerReplyPermission` and
  `github_pull_request_snapshot::ConversationLock`, exactly when the shape asks.
  The projection hands them to the conversation as `ViewerCanReply` and
  `ConversationLocked`. A schema without them leaves both unavailable.
- **Core decides** (`core::decide_thread_reply`). A live probe on BPR-Test#135
  showed that GitHub's `viewerCanReply` already weighs the lock: on a locked
  pull request it was false for `MikeMarcinTest` (read access) and true for the
  owner. So `viewerCanReply` false refuses the reply, as `locked` when the pull
  request is locked and `viewer_cannot_reply` otherwise. The lock alone refuses
  nothing. This narrows [[BPR-1745]]'s rule ("one on a locked pull request takes
  none"), which would have refused a collaborator GitHub lets reply;
  RFC-BPR-0028's amendment records it.
- **Qt presents** (designed with the `frontend-design:frontend-design`
  skill). A refused thread's open card has no Reply field. In its place one
  quiet line, at 0.92 of the card's size in its secondary ink like the
  outdated note, says "This conversation is locked. Only collaborators can
  reply." or "GitHub doesn't let you reply in this thread." The menu's Reply is
  disabled with the same words, and R shows them as the drawer's notice. The
  composition makes no draft for a refused thread.

## Not in scope, and left open

- A file-level thread's reply is unchanged ([[BPR-1745]]'s open point).
- The lock alone refuses nothing on a schema with `locked` but without
  `viewerCanReply`; GitHub decides at Publish there.
- Contract trees whose builder has no regeneration row (overview labels,
  conventional comments, header source, C++ identifiers, the markdown trees,
  insights budget, status attention, github-com and ghes-3.18) took the two
  fields by hand, after `viewerCanUnresolve` and `headRefOid`. A builder run
  writes the same values in its own key order.
- The device-authorization route probe captured in
  `tests/fixtures/github/device-authorization/v1/route-probes.json` is a
  historical capture and keeps its document.
