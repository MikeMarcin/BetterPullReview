## Procedure for the next run

The criterion was the four rows. A red row elsewhere in the suite was recorded,
but it did not fail BPR-0905 unless it was a clock failure that the rule
should have caught. A rerun reports:

1. `HEAD`, the product-path diff against the candidate, core count, and load
   at the start and end of the run.
2. The total rows, passed, failed, and the `Total Test time (real)`.
3. For each of the four rows: the result, the row time, and every
   `PUBLIC_PATH_BUDGET` line for the three application rows, from the full
   run's own `LastTest.log`.
4. Each failing row with its one-line headline, and whether it is a clock
   failure (`RUN_BUDGET_EXPIRED`, `PROCESS_TIMEOUT` or `***Timeout`).
5. That platform's margin table, built from the `json-v1` inventory and the
   run log: every passing row whose explicit `TIMEOUT` is less than three
   times its duration in this run, with its timeout, duration and ratio, plus
   the count of rows with an explicit `TIMEOUT`.

**Order matters.** Every `ctest` invocation rewrites
`Testing/Temporary/LastTest.log`, and `--show-only` is no exception. With CTest
4.4.3 on the Mac, a log holding a `PUBLIC_PATH_BUDGET` line held none after
`ctest --show-only=json-v1`. So these commands take the inventory before the
full run, and copy `LastTest.log` as soon as the run ends, before any other
`ctest`. The first Linux run here took the inventory after, and its budget
lines had to come from a serial rerun.
