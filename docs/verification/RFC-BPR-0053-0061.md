### BPR-1150: bytes, modes and special files

Owned paths: `src/core/include/bpr/core/review_cycle_material.hpp`,
`src/core/src/review_cycle_material.cpp`, the streaming `sha256_stream` added
to `bpr/core/sha256.hpp` (the one-shot `sha256` now uses it),
`tests/core/review_cycle_material_tests.cpp`, the port's optional execute bit
(`workspace_entry_observation::Executable`, absent on Windows) and the
BPR-1150 rows of `tests/workspace_contract/review_cycle_capture_tests.cpp`.

`core_review_cycle_material` classifies a byte-golden corpus (empty, LF, CRLF,
CR, mixed, trailing CR, no final newline, UTF-8 BOM, UTF-16 LE/BE marks,
overlong, surrogate, truncated and Latin-1 bytes, NUL binary, multibyte) and
gets the same profile when the bytes arrive one at a time; recognizes an LFS
pointer and not materialized content; maps byte offsets to columns only at
scalar boundaries; and streams the same SHA-256 as the one-shot function.
`review_cycle_capture` (macOS arm64) captures the corpus from disk and reads
every retained object back byte-for-byte equal to the original file, with the
raw hash equal to SHA-256 of those bytes; CRLF, BOM and a missing final newline
are kept; UTF-16 and invalid UTF-8 are file-level only; the execute bit maps to
100755/100644 and removing it alone produces new material; a link is kept as
its target bytes and never followed; a FIFO is visible as unsupported; a file
over the request's budget is visible as too large and not read. In a Git root
with index version 4, a submodule gitlink is a boundary carrying its staged
commit and is not recursed, and `*.bin filter=lfs` marks both a pointer blob
(recognized) and materialized bytes (kept as read, never cleaned) as
filter-managed.

Limits: case/normalization collisions are the core rule from BPR-1148; the
Windows row that a new file gets no invented execute bit is written but owed
to the Windows station, as are Windows link targets (reported unsupported).
Encodings other than UTF-8 are not decoded at all, by design.
