# BPR-1770 — direct requested-review discovery

Mandate `home-requested-repairs-r1`, owner authorization 2026-10-26.
Baseline `e6e69cc2c6a429209ac3462579a4cb685855fa86`. This is a follow-up
to BPR-1680 and BPR-1694; their historical acceptance stays unchanged.

## Behavior and limits

GitHub.com and the selected GHES 3.18 contract document
[`user-review-requested:@me`](https://docs.github.com/en/enterprise-server%403.18/search-github/searching-on-github/searching-issues-and-pull-requests#search-by-pull-request-review-status-and-reviewer)
for direct user requests. Both the core search planner and the canonical REST
search compiler use that exact qualifier. Authored search still names the
validated viewer. Repository query batching retains its 256-byte/ten-repository
bound, now calculated with the exact direct-user qualifier. Account acquisition
and `/user` authority checks are unchanged.

For unknown requested candidates, each GraphQL batch names at most ten PRs of
one repository. It selects repository/PR identities, number, open state,
head/base revision and base ref, and the first 100 review requests with user node
and login, team node, request node, total and cursor. It does not ask for
reviews, checks, merge facts, team descriptions or organization metadata.
A direct match requires both the exact viewer node and case-insensitive login.
A team never matches the viewer. Search alone never establishes membership.
Each roster is exhausted before an absence or match is published, with stable
identity/revision/state/total, unique request/actor nodes and cursor guards.
The same 1,000-roster-record, ten-pages-per-PR and shared 32-request/8-MiB
membership budgets remain enforced. Caller page/byte/structural limits and
cancellation still apply. Only an unsupported GraphQL schema permits complete
REST fallback; authentication, malformed identities and rate limits do not.
REST size-limit recovery now combines its narrow anchor and first roster page.
Only confirmed direct matches receive optional Home summaries.

Only complete retained reads from this refresh are reused. Negative membership
is never cached across refreshes. Search-page, candidate and summary limits
preserve the existing partial-result/withdrawal semantics.

## Safe diagnostics

Standard discovery records append `candidates`, `reused`, `direct`, `rejected`,
`roster_recoveries` and closed `completeness` reasons. Direct/rejected count
newly validated candidates; retained reuse is separate. Recovery counts rosters
requiring continuation or REST-limit recovery. Reasons distinguish complete,
incomplete search, search result limit, candidate limit, roster limit, summary
limit and multiple independent limits. Read and refresh totals travel through
the real provider/host/core/logger. Retained reads also report an existing
optional summary bound as `summary_limit`, including the batched path. The log schema remains compatible: both
historical discovery line forms still parse and export. New paged-operation
names are appended to the closed logger/export vocabularies. Extra fields,
unknown reasons and private payloads remain refused.
