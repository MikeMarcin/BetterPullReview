A - the whole review in one place

Every thread across every file in one surface, grouped by file, plus the pull-request-level reviews and comments that the file-anchored drawer never shows at all. Choose this if the case you hit is 'I have lost track of what is still open across this review', rather than 'this one thread is too tangled to follow'. It reads the projection exactly as it is today: the only change is dropping the current-file filter and grouping by Path, so no model change and no fetch change is implied. Its real cost is a second surface that has to stay consistent with the drawer, and a second place a reviewer can lose their position.

B - a Treeverse-style map of one deep thread

A map of one thread's reply structure, with the path from the root to where you are highlighted and one reply in focus. This is the alternative your own reference points at: Treeverse, which you reach for on Twitter threads because a linear presentation gets confusing at depth. Choose this if the case you hit is 'this one conversation is too tangled to follow inline'. Two things to weigh. First the cost, which an earlier draft of this page got wrong. The reply edge is already fetched and validated - the read model carries ReplyTo per comment - and the projection throws it away at github_projection_mapping.cpp:175, writing the thread root as every comment's parent. That much is true. But changing only that line would make the drawer WORSE: github_conversation_model.cpp:317-326 accepts a parent only when the parent is a review_thread, so every reply would be rejected and promoted to a root, flattening two levels into one. The real change is the mapping, that filter, a fallback for the null ReplyTo a thread's first comment carries, and the tests that encode today's shape. Second, and unchanged: nothing in this repository could exercise it. The conversation drawn here is invented.

Details and identity

Acceptance criteria

  • Depth is a real problem worth a second view, not a hypothetical one
  • A map plus a focused reply is the right shape for it, rather than better inline nesting
  • It is worth building before a conversation deep enough to need it has ever been recorded

Known concerns

  • The conversation shown is SYNTHESIZED. No recorded pull request here has any conversation, and the deepest real structure in any fixture is one replyTo edge - so this design has never been seen against real content
  • BPR-0211's own stated precondition, that a conversation deep or wide enough to be a problem is recorded, is still unmet
  • GitHub's own review threads are largely flat in practice, so restoring the reply edge may yield less depth than this map suggests
  • The cost is not one line. It spans github_projection_mapping.cpp, the Qt model's parent-kind filter, a null-ReplyTo fallback, and two test files; the naive one-line edit flattens the drawer rather than deepening it
  • The map legends a per-node read/unread state that the product does not carry. github_conversation_projection has no read flag; the ledger's unread notion is a per-conversation cursor, so that state would have to be built too

What this would cost

  • github_projection_mapping.cpp:175 - carry comment.ReplyTo instead of the thread root, with a fallback for the thread's first comment, whose replyTo is null.
  • github_conversation_model.cpp:317-326 - stop rejecting a parent whose Kind is review_comment, or the change above flattens the tree instead of deepening it.
  • A new map surface plus its focus pane, keyboard navigation, and accessibility.
  • Per-comment read state, which nothing currently carries.
  • Tests that encode the two-level shape today, in the application host and the Qt panel.
  • A recorded conversation with real depth, which does not exist yet and cannot be manufactured honestly.

Conversation and code on the same revision axis - worth an RFC?

A separate question from the one above, so it is a separate decision rather than a third alternative. This is the thing you said GitHub is extra terrible at: seeing conversations and code evolve together as a PR gets new revisions. The mockup shows what it would look like if a comment knew which revision it was written against - which comments were live on each side of a comparison, and what went outdated in between. Accept means it is worth writing the RFC that this needs. Reject means not now, and the card stays recorded rather than started. Be aware of what the mockup is: the epoch axis is real and the conversation axis is real, but the join between them is not. github_conversation_projection carries no commit OID, no epoch, and no ordinal, so every cell in that grid is a value the product cannot compute today. Outdated is a boolean GitHub handed us with nothing behind it.

Acceptance criteria

  • The join is worth having enough to justify a model change, not only a view
  • An RFC is the right vehicle, because this crosses the conversation model and the epoch axis
  • It is worth doing before the earlier RFCs in the canonical order close

Known concerns

  • The narrow open question is whether the per-comment commit can be read: the review-thread GraphQL selection asks for originalLine but not the comment's commit, and whether it is available unauthenticated has not been checked. An earlier draft of this page put that far more broadly - 'whether GitHub exposes it at all' - which this repository's own code falsifies
  • This crosses RFC-BPR-0002's conversation model and RFC-BPR-0003's epoch axis, so two owners have to agree before a field is added
  • The card explicitly warns against adding a revision field to the projection as a side effect of a presentation card, which is the cheap path this must not take; accepting this subject authorizes an RFC, not a field

What exists and what does not

The revision axis - exists
accepted_pull_request_revision carries Base and Head OIDs; epoch_comparison_control already offers independent left and right selectors over retained epochs
The conversation axis - exists
github_conversation_projection carries Path, Line, Resolved and Outdated for every node
A review's revision - fetched, then dropped
github_read_model.hpp:223 carries an optional commit per review and github_read_contract.cpp:1214-1241 requires commit_id on every review object; github_projection_mapping.cpp:145-156 then discards it
The write path already does this
github_mutation_contract.cpp:117-122 sends commit_id - the exact anchor commit - when BPR creates a review comment, and rejects a mismatched echo
A comment's revision on read - not requested
the review-thread selection in github_read_contract.cpp asks for id, bodyText, path, line, originalLine, outdated, author and replyTo; no commit field

Why this is not a slice

  • It changes what a conversation is in the model, which is RFC-BPR-0002's territory.
  • It consumes the epoch axis, which is RFC-BPR-0003's.
  • It implies a fetch that records the revision a comment was made against, whose availability has not been checked.
