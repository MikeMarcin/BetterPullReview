Is marking the line above a change group the right place for a hunk boundary?

A hunk header cannot be a row of text here. These panes show whole documents side by side, so inserting a header row would make pane line N stop being document line N, and every mapping built on that equality would shift by the number of headers above it. The delimiter therefore has to be a marking on a line that already exists. I put it on the unchanged line immediately above each group, which is otherwise untinted. This is my choice, not one you approved, and it is the only placement the mechanism allows without custom viewport painting.

Boundaries above each change kind

The marked line is the unchanged one directly above each tinted block.

Acceptance criteria

  • The boundary reads as a delimiter between change blocks rather than as a change
  • Giving an unchanged line a role it did not have is an acceptable cost
  • The alternative — taking a changed line's own tint to mark the boundary — would be worse

Known concerns

  • An unchanged context line now carries a background it did not before, which could read as 'this line changed'
  • diff_hunk_header_text is applied as a foreground on that line, so the context line's own text is recoloured
  • A group starting at the very top of a file has no line above it and is not marked at all
  • The only alternative placement, custom viewport painting, perturbs the pane geometry RFC-BPR-0005's measured-axis and bounded-widget evidence rests on

Why not a header row

The constraint
pane line N must equal document line N, or intraline emphasis, token spans, selection, and the measured axis all shift
What breaks
every mapping built on that equality, by the number of headers above the line
What is left
a marking on a line that already exists, or custom viewport painting
