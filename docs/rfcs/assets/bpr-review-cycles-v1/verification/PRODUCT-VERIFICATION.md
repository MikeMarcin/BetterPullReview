# Product verification contract

The 90 acceptance rows are implementation obligations. Every row starts **Not run**.
The archive's reference tests validate only the supplied contracts/examples and pack
structure; their passes must not populate product rows or be called native import,
application build, host security, human approval, model or GitHub execution evidence.

## Required evidence record

Record criterion ID, exact production check/test or human gesture, observed result,
producing source revision, environment/build/configuration, and limitations. A related
code path or test source is not an observed pass. A cross-compiled executable is not
native execution. Unsupported current platforms/capabilities remain explicitly blocked
rather than gaining synthetic success through a fallback.

Use focused checks per card plus the affected integration boundary. Do not rerun an
exhaustive historical matrix on every small change. Critical scrutiny belongs at byte
identity, authority, filesystem admission, import, storage and publication boundaries.
Use existing native/attended-review and issue-board machinery, not a new ceremony or
model-dependent verifier. Unchanged evidence may be reused with its original revision
and applicability explained; do not relabel it as newly observed.

## Evidence lanes

| Lane | Must establish |
|---|---|
| Pure core | Cycle/round/revision separation, state legality, exact comparisons, suggestion conflict rules, immutable delivery selection, provenance and verification distinctions. |
| Application/adapter | Real filesystem/source material, persistence recovery/pins, coherent owner access, no stale target dispatch, actual byte-safe render/export/import, no implicit execution or network. |
| Native desktop | Full-source reading and selection, editor virtual space/IME/undo, related notes, stable tabs, share and capture surfaces in the accepted scaffold. |
| Installed agent-free package | No linked/installed agent helpers or provider runtime dependencies; complete manual two-round loop, CLI where installed, restart and publication preparation remain functional. |
| Automation-off package/policy | GUI clipboard/file/manual iteration still works when local automation is independently absent/denied. No hidden alternate listener. |
| External consumer | Exact scoped complete assignment, current-harness operation, optional item-linked reply; no callback required for source capture. Candidate skill installation needs its own authority. |
| Direct adapter | Same canonical payload, correct explicit profile/session, truthful send/ack/completion distinctions, stale output isolation, manual continuation after removal. |
| Publication | Candidate tree and metadata, finite authorization, admitted native operations, read-first uncertain-effect recovery, actual new-ref/PR verification, no user-checkout destruction or private-history upload. |
| Security | Adversarial paths/bundles/input, revoked scopes, cross-cycle isolation, exact context selection, content-free diagnostics and documented same-user/external retention limitations. |
| Human workflow benefit | Fixed task/source harness, preparation time, steering turns, missed requirements and rework; report negative/mixed results instead of presuming token savings. |

Native Windows/macOS/Linux runs must name the actual supported target and relevant
current project qualification gates. GitHub.com/GHES live writes require a designated
disposable repository and explicit authority; unauthorized absence of such a target
is not permission to test on company PRs. A fixture cannot establish server-version
support, actual credential scope, branch protections, authorship, API races or cleanup.

## Failure and cancellation

The scenario corpus names required production cases; each row needs a concrete test
or explained blocked environment. Include failure after an external effect but before
its receipt. Do not promise transactional rollback across filesystem/SQLite/network
boundaries. BPR never deletes foreign branches or force-pushes to “clean up” an uncertain
publication. On restart, recover reads first and obtain current authorization for
remaining writes. Local histories retain exact references or explicit unavailability.

## Closeout

Cards 44–52 each own one RFC closeout with closeout_for. Reconcile the live canonical
order and predecessor gates, run the real documentation/board checks, and preserve
unmet owner/native/live criteria. A blanket report that the pack passed its Python
checks cannot close any product RFC. Keep artifact validation in PACK-VALIDATION.json
and product evidence in the live per-RFC ledgers and acceptance matrix.
