# Author and reviewer experience

## Author: no AI configured

Open an existing draft PR and choose **Prepare review tour**. Problem is the initial section, with a Markdown editor, optional preview and short coaching. Solution is a separate section with its own text. Both can be filled from existing PR source by deterministic section mapping; a blank PR remains blank until the author writes.

Open Tour stops, select the code that best introduces the change, and choose **Add tour stop**. Write a title that names the idea, not merely the filename. Add the next relevant location, even when it is earlier alphabetically or in the same file. Reorder by drag or keyboard. Related code links support the explanation without demanding extra stops. Leave the tour to inspect a caller and return without losing the editor or route position.

Preview the Problem/Solution and actual GitHub index/stop comment Markdown. Show exact destination/actor/head and the publication boundary. The no-AI path provides a short optional checklist, not an assessment score. Nothing invokes AI or writes remotely before Publish. After success, the author sees ordinary review/comment links that work in a browser.

## Author: optional assistance

The magic button is secondary. With a selection, its label/tooltip is Enhance selection. Without one it enhances the current field; an empty field uses Draft from PR context. The existing text stays in place while a cancellable request runs. Completed text replaces only the captured span, once, with one native undo entry. There is no side-by-side suggestion panel and no Apply/Dismiss UI. The author can Undo, Redo or invoke Enhance again on the current selected replacement.

The Problem/Solution/Comment writing hooks are independently configured. Selection is an invocation scope within those hooks, not another skill. A private inline context-status note may explain recovered/inferred material or an uncertainty without becoming published prose.

Suggest tour outline proposes only titles/destinations/prompts. It does not fill comments. Entries remain Suggested until visited. On a selected entry the author may write manually or explicitly draft that one comment. **Ready and next** acknowledges the actual displayed current stop, not an AI proposal. Unseen asynchronous output is never Ready because the placeholder was previously opened. There is no bulk generate-all or bulk Ready command.

## Reopen and maintenance

On another BPR installation, select the published index and reload the PR text/comments. No AI is needed. Website edits are loaded as remote truth. Local-versus-remote divergence opens a clear conflict view; it does not silently pick a version.

Reorder published stops without replacing comment IDs or losing replies. Insert creates a new review batch where possible and joins its new comment links to the existing index. Remove from tour changes membership, not GitHub history. A source retarget is different from reordering: show the old thread and the new destination and use a linked replacement when the old native anchor is immutable.

## Website-only reviewer

The description leads with Problem and Solution and links to Start here. The review summary provides the order and actual comment links. Each stop explains its own local point beside the code or provides an exact source permalink for a compatibility subject. Previous/Next/Tour overview work without BPR. The reviewer replies normally and can inspect any unmentioned part of the diff. Resolving a thread is a normal GitHub action; BPR does not resolve tour explanations automatically to reduce merge chores.

## Useful defaults, not prose quotas

Prefer a small meaningful route. Expose the central decision, evidence and uncertainty rather than narrating boilerplate edits. Do not hide important risks in collapsed disclosures or require one. A one-sentence Problem is fine. A table helps a comparison, not every field. Do not turn optional reviewer guidance into management metrics, dwell-time monitoring or automatic approval pressure.

## Accessibility and layout acceptance

Require native keyboard traversal, labelled controls, exact selection restoration, focus preservation when toolbar buttons are clicked, keyboard outline reorder, screen-reader ordinal/status announcements, visible cancel/error state and no focus stealing on late responses. Test narrow/wide windows and larger fonts. Avoid nested scrolling that strands the comment editor or code destination. Use the current theme tokens and Markdown reader, without WebEngine or automatic remote images.

The pack specifies behavior rather than supplying fabricated “approved” screenshots. Final implemented layout needs target-native captures and a website-only walkthrough tied to an actual candidate. Existing accepted workbench layout remains the starting point.
