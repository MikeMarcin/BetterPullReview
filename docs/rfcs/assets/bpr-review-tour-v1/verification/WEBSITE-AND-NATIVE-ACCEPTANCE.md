# Designated website and native acceptance

This is an operator course, not authorization to mutate any live PR. Use an explicitly approved safe test repository/PR and the project's existing attended/live authority workflow. Bind host, actor, candidate revision and each publication plan. Retain sanitized facts and actual observations; do not collect unrelated private code or tokens. Never make scratch writes to a company PR to discover support.

## Course

1. On the candidate app, open an existing draft PR with a short or unstructured description. With no AI configured, write/map Problem and Solution, add at least three manually authored stops in a non-file order, include a range and a related source link, and reopen the draft locally. Verify no remote edit or draft-status change occurred.
2. Preview the actual normal-comment output and exact actor/head. Start one staged native publication. Inspect the pending review from the author's website view and confirm the expected comments/IDs/navigation; separately verify absence from a reviewer account before submission where the environment permits. Do not treat a simulator result as this observation.
3. Submit COMMENT once. From a reviewer account using only the website, follow the index to every stop, Next/Previous/overview and pinned code links; reply under an ordinary stop. Record whether collapsed/resolved/outdated display affects following the route. No hidden markers or BPR install instructions are needed.
4. Reopen BPR from an empty local test profile/store and recover brief, order and comments without AI. Edit one comment/description section on the website and refresh. Preserve unrelated template text. Deliberately diverge local and website text and resolve the visible conflict.
5. Reorder the published route, add a stop in a later batch and retire a replied-to stop from the route. Confirm original comments/replies persist and the index spans batches. Interrupt an update at a controlled safe point, inspect partial state, reopen, reconcile and explicitly resume with no duplicate creation.
6. On a separate approved compatibility case, qualify file-level pending staging and the exact canonical permalink. For an unbatchable historical/untouched target, confirm the app explains the non-atomic plan before any standalone visible write and that the website still receives a useful normal comment/code link.
7. In the native app, configure one writing profile and explicitly test the four hook controls. Select a phrase, click Enhance, inspect replacement, Undo and Redo; preserve toolbar selection and count zero new inference on Redo. Repeat with emoji, CRLF and multiline selection, then edit while a response is pending. No Apply/Dismiss panel appears and newer writing is untouched.
8. Suggest only an outline. Confirm empty bodies and explicit visits. Generate one stop while visible, leave before a second test response arrives, and verify it cannot become Ready unseen. Complete or remove every retained entry manually; no bulk completion exists.

## Host/transport matrix

Repeat only the rows necessary for each **claimed** operation/placement/transport: native HTTPS on eligible platforms; currently admitted macOS `gh api`; GitHub.com; supported GHES floor/deployments; line/range; file subject; standalone compatibility; pending-body edits; submission; published-body edits. Unsupported CLI platforms remain unsupported. Document actual server/client versions where observable; do not infer capabilities solely from them.

## Native usability subjects

Keyboard-only creation/reorder/navigation, text selection and IME, exact undo/redo, light/dark/high-contrast themes, current display scales, narrow/wide windows, large fonts, no nested scrolling trap, busy/cancel/error announcements, and no focus theft by a late response. Record separate subjective verdicts rather than inferring approval from a successful screenshot generation.

## Result template

For each criterion retain: observed/not-run/fail; candidate revision; host/transport/platform; safe target binding; source observation or capture; actual outcome; limits; operator confirmation where required. The default status is **Not run**. A missing real-service/account/native environment stays explicit and cannot be filled with an invented pass. A fixture-only implementation may be technically complete while those release capability gates remain open.
