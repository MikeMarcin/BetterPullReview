Where Compose review and Draft comment or reply sit

BPR-1106, design round v1, for the owner. Five placements are drawn on the accepted RFC-BPR-0028 full review surface. The current row is placement A, the baseline. Each is drawn at 1280×852 and 1920×1080, in light and dark, in macOS and Windows chrome, and once more while a pull request loads. That makes 50 frames, rendered headless from one frames file, so any two frames differ only in the placement.

We should do a UX design iteration with the /frontend-design skill to figure out where best to put these. For now you can ammend the card but open a follow-up for the ux design.
The owner, on BPR-0653-entry-row-v001, attended session cbd48b91, decision 007a6eb5, 2026-09-24.

The question, one choice: where do Compose review and Draft comment or reply go?

  1. AKeep the row as it is, between the strip and the Updates line.
  2. BIn the strip's review menu: the Private progress button's menu gains a "Your review" section.
  3. CAt the right end of the Updates line, beside "Comparing"; the loading line moves into the Updates line too.
  4. DAt the foot of the conversation drawer.
  5. EA Compose control in the strip: one click composes a review, and its arrow offers Draft comment or reply.

Proposed: C. It frees the comparison's 20 to 22 pixels, adds nothing to the Windows strip, and keeps one click to each entry. It also gives the loading line a home that does not push the window down.

Why C is proposed

  • It gives the comparison its pixels back (22 on macOS, 20 elsewhere, in every mode) and puts nothing in the Windows strip, which has no room.
  • It keeps one click to each entry, with labels always in view. Among A's virtues, only these two could be kept for free.
  • It settles the loading line too. Today a 28-pixel row comes and goes above the chrome while a pull request loads. In C the words sit in the line's empty track, so the window does not jump when loading ends.
  • Its cost is the Updates line's track: 303 pixels of it at every width, which at 1280 still leaves 697. At the narrowest windows the labels give way to icons.

Runner-up: D, if composing should sit with the conversation. Its gap is the hidden drawer. B is the cheapest to build but hides both entries. E is the familiar toolbar answer, but it spends width the Windows strip does not have.

How the frames were made

Every frame is the frames file with query parameters for placement, appearance, platform, size and state. It uses the accepted surface's tokens as they are. Headless Chrome rendered each one at exactly its window size with device scale 1, and each was then reduced to a 256-colour PNG. The frames were looked at, not only written.

The heights are exact for the mock and match the product's row heights: 22 on macOS and 20 on Windows, measured by BPR-1036 and BPR-0653. The Windows floor numbers are BPR-0653's measurements of the product, not the mock's. On this Mac the Windows frames fall back to the Mac's type, so their widths are indicative. At 1280 the Windows frames take the compact modality labels, the yield the product takes first.

Out of scope here: shortcuts for the two actions, and showing whether a draft is kept. Either can be added to any placement on its implementation card.
