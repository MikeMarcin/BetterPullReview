Recommended

  • One Ask control at three anchors. The review bar asks about the pull request, the file’s header about the file, an open thread’s reply row about the thread. It is the same button and the same menu each time. In the file’s header it takes the place of Explain this file, and in the reply row it joins tools that are already there, so no new row is added anywhere.
  • The menu holds quick asks only: the suggested prompts with Quick ask ticked. A row’s right end says what a press will read. Custom question… opens the Agent tab on that subject and sends nothing.
  • Hide what is not here; grey what is here and cannot run yet. A greyed row’s tooltip gives the reason.
  • Was this addressed? is one quick ask at three scopes, on any thread. On a thread it asks about that thread, on a file about each of its threads, on the pull request about all of them. Nothing is restricted to threads I commented in.
  • A claim lands as one chip in its thread’s header. No height is added and nothing moves. A press shows the evidence over the code.
  • A short answer is a reply where it was asked. A long one is a report card there, and the card opens the report as a file tab, beside the files’ tabs, with an outline. The Agent tab, the Tour tab and the tour’s chat keep their places and stay usable, and a code reference is one press to its line and one press back.
  • What changed is grouped by area, and a merge of main is one line wherever commits are listed.
  • The macro editor gains one row: a Quick ask checkbox, and Thread, File and Pull request as toggles that can each be on.

1 · The Ask menu

Option 1C’s pull-down, kept where it was: in the review bar, beside the comparison. It no longer lists every suggested prompt. It lists the quick asks, and the rest stay chips in the Agent tab as RFC-BPR-0125 has them.

What it gives
  • One control for every agent question, however many arrive. A row is one press from a run.
  • The menu is short because it is curated: a prompt is in it only when I ticked Quick ask.
  • Every scope is reachable from one menu, so the keyboard has one place to go.
  • The button is ordinary. Its glyph and its rows carry the accent, because the rows start runs and the button does not.
What it costs
  • Was this addressed? is in the menu three times, once a scope. The sections and the counts tell them apart.
  • Fifteen rows when a file is open and a thread is selected. Question 2 is the shorter form.
  • A point on the button is all that says something returned. The returning question is the menu’s first row.

3 · Answers

A short answer is a reply where it was asked, as now. A long one (What changed after a large push, Explain this file, a check across many threads, a tour’s What’s not covered?) is a report card in the chat: its title, what it read and its first lines. The card opens the report.

Where the report opens: one report, three hosts

The report is the same component in each: a line saying what it read, an outline, the text. Each is drawn twice: opened from the Agent tab, and opened from the tour’s chat, where the window already holds the code, the Tour tab and the chat. A reader pane beside the chat and a tab in the window’s own row are not drawn; the owner set both aside.

1 · A file tab (recommended)

What it gives
  • The chat and the tour stay in view and usable. Nothing is added beside them and nothing is laid over them.
  • To the code and back is one press each way, and the report is where it was left.
  • Tabs are already how this window holds more than one thing to read. Two reports are two tabs.
  • It scales with the change: eighteen commits are four areas of a few lines each, and the outline is the way through them.
What it costs
  • It is as wide as the code area. With the tour and its chat open at 1280 that is 388 points of text: readable, not generous.
  • The code is not visible while the report’s tab is active.
  • The review bar’s file controls have nothing to act on, and a tab must be able to hold something that is not a file.

2 · A lightbox

What it gives
  • The same generous size wherever it is opened from; the layout under it does not matter.
  • Nothing moves and nothing new stays on screen afterwards. The least to build.
  • It is the popup the owner first described.
What it costs
  • Reading is all it allows. To add a stop, answer a thread or ask a follow-up, the report closes first.
  • A code reference closes it, and coming back means finding its card again.
  • One report at a time.

3 · A window of its own

What it gives
  • The only host that can show the report and the code together, on a display with room.
  • The pull request window is left exactly as it was, at every width.
  • It can go to a second display.
What it costs
  • A window to place, find and close. A press in the pull request window puts it behind.
  • On a laptop display it covers the code, as the lightbox does, without the lightbox’s way out.
  • One more entry in the Window menu a report, and a lifetime to settle: it goes when its pull request window does.

A check across many threads, as a report

4 · What changed, and a merge of main

Option 1A listed every commit with its changes, which is right for three commits and wrong for thirty. The report is grouped by area, each a few lines, and the commits are a list at its end. A merge of main is one line in that list, in the card and in the line that says what the report read. Its changes are not narrated and its commits are not counted as the pull request’s.

5 · The macro editor

One new row in the sheet of RFC-BPR-0125, and one more word in a row’s state.

What it gives
  • One row. Ticking the box turns on the prompt’s own scope and most prompts need no more.
  • One prompt serves a thread, a file and the pull request, so there is one name and one text to edit.
  • The toggles are the three anchors, in the same words the menus’ sections use.
What it costs
  • A scope wider than the subject means a run for each. Only the toggle’s tooltip says so in the sheet; the menu row’s count says so where it is pressed.
  • RFC-BPR-0125 gives a macro one place. This gives a quick ask up to three.

Open questions

  1. Grey or hide. Is the rule right: a quick ask is hidden when its subject is not there (no thread selected, a path rule that leaves the file out) and greyed with a reason when it is there and cannot run yet (no commits since, no failed check, no threads on the file)? The two pure treatments are drawn beside it.
  2. What the review bar’s Ask lists. As drawn it lists the pull request’s quick asks, then the open file’s, then the selected thread’s, so one menu reaches everything by keyboard. The alternative is the pull request’s only, five rows, with the file and the thread reached from their own controls.
  3. The file’s header. Ask is drawn in the place of the Explain this file control RFC-BPR-0117 put there. Is that right, or does Explain this file keep a control of its own beside Ask?
  4. Where Explain this file answers. RFC-BPR-0117 shows the answer in a card under the file’s header. Here it would be a report card in the Agent tab that opens as a report, like What changed. One pattern for every long answer, at the cost of the answer no longer opening on its own over the file.
  5. One press, how many runs. Was this addressed? on a file or a pull request is drawn as one run a thread, so claims arrive one by one and each thread’s chip is its own answer. Twelve threads cost twelve runs ($0.19 in the frame). Should a large count ask first, and from how many?
  6. The baseline for a thread I did not write. RFC-BPR-0116 compares with the commit my last comment was written on. For any thread the frames compare with the commit the thread started on. Or should it be the thread’s last comment?
  7. What makes an answer a report. Recommended: its shape, not a setting. An answer with sections, or longer than the tab shows without scrolling, folds into a card; What changed, Explain this file and a check of more than one thread always do. The alternative is a second checkbox in the macro editor.
  8. Which host. The file tab is recommended. The lightbox is the least to build and the worst at going to the code and back. The window is the only one that shows the report and the code together, and only where there is room beside. A tab could later be moved to a window of its own from its menu, which would give both.
  9. The review bar while a report’s tab is active. File 2 of 14, Changes 3 of 9, Seen, Read, Accept and the file’s Ask are about a file. They are drawn in place and off. Is that right, or should the bar keep showing the last file’s?
  10. Is a report kept? A report’s tab can be closed and reopened from its card while the turn is in the chat. RFC-BPR-0101 makes a first answer a fresh run with nothing saved. Does an open report’s tab come back when the window is reopened, or only through Save as note?
  11. The merge line. What should it say after its count: nothing, or whether the merge changed this pull request’s files (as drawn)? And is a rebase onto main one line in the same way, “Rebased onto main (24 commits)”?
  12. One prompt at several scopes. RFC-BPR-0125 says a macro has one place. The toggles let one prompt about a thread be offered on a file and a pull request, where it runs once a thread. The smaller alternative keeps one scope a prompt and ships Was this addressed? three times.
  13. The three agent actions are not suggested prompts today. What changed, Was this addressed? and Explain this file each have a built-in prompt of their own and no row in Suggested prompts. The frames assume each gains a built-in row, so Quick ask and the scopes are set in one place; what they send stays in Built-in prompts.
  14. The claim’s colour. The chip is drawn in ordinary roles with the glyph in the accent, because a press on it starts nothing. The last round drew the claim in the accent’s wash. Which?
