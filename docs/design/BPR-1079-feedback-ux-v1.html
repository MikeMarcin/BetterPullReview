BPR-1079 (RFC-BPR-0048, 0049, 0050; R30, R33). 2026-10-05. Frames: BPR-1079-feedback-ux-frames-v1.html, each drawn at a real window size (1440×820 wide, 960×700–760 narrow, Settings at its 760×560 minimum) in the app's light palette, three also dark.

None of this is implemented. These are static design frames. The owner's selection is pending in attended review. BPR-1081 records it, and only after that does design-dependent work start (R30). The two-letter squares are placeholder marks: they stand in for the twelve icons, which are BPR-1080's work. They propose no metaphor or colour, and none comes from the chat.

Rules every candidate keeps

Counting unitOne conversation (a native thread, a top-level comment or a review summary) counts once, classified by its root. Replies carry their own marks but never add to a count. Every column header and count tooltip says "conversations" and "replies don't count".
Other (catchall)The existing Comments counter becomes Other as soon as any label has a column: plain comments, labels without a column, custom labels and unreadable roots. With no label columns it keeps its name and counts everything. Dedicated columns + Other = the included conversations, in every scope. The frames compute this from unit data, and HairStrandsLighting.cpp is the pack fixture's src/cache.cpp: Open gives issue 2, question 1, Other 4, total 7, and All gives issue 4, question 1, Other 5, total 10.
Not on a fileA last row holds unanchored threads, PR-level comments and review summaries, so file rows never claim them and the PR total stays honest.
ResolutionFour states, each with its own round mark: open (amber dot), resolved (green tick), unknown (dashed ring with ?) and not resolvable (ring with a dash). Open is the default count. All counts every conversation and adds a small state bar under each number. Unknown and not-resolvable conversations are never shown as resolved or as a clean zero. A ? chip beside the switch counts what Open leaves out or can't classify and lists those conversations in Discuss.
Labels vs statesLabels are square and states are round, so a label never shares a shape with a state. Colour belongs to states and only ever adds to a mark and its words. A resolved issue still shows its issue mark.
IdentificationEvery mark has a tooltip and an accessible name with the label's word. A keyboard-reachable Label key button (⌥K) shows all twelve marks with their names, so a hover isn't the only way to learn them.
Drill-downClicking a count opens Discuss filtered to that file, label and mode: the same conversations the number counted.
Public vs localA label is public text at the start of the comment. The editor shows it highlighted in the Markdown, the preview shows exactly what GitHub gets, and Copy source keeps it. Private defects keep their own dashed, locked badge and never become a public label. Drafts, private notes and pending posts are never counted.
Native reviewComment, Approve and Request changes remain explicit choices that the reviewer makes. No label resolves, approves or requests changes, and nothing is sent before Submit review or Publish.
SuggestionsA suggested-change block keeps its own header and is never restyled by a label. A tick (or ↗ Apply on GitHub) appears only where GitHub can apply it. A struck-out ↗ marks a fallback that GitHub cannot apply.

4. Labels on thread cards (one proposal)

The root's mark and label head the card, and the round state pill sits at the right. The card body starts after the prefix, which the mark stands in for, and Copy source keeps the prefix. A reply shows its own mark, which can differ from the root's. A tour stop is plain unless its author labelled it. The private defect badge is dashed and locked.

5. Before submitting a review: A or B

The disposition becomes three visible buttons. Approve carries an amber dot while I have open blocking feedback, and its tooltip says that approving doesn't resolve it. The section holds the label helper (off by default), the default count (Open) and the columns, which you tick and drag to order with a preview of the Overview header. Reset applies to this section only. It uses the existing typed settings store, and the Comments drawer's own filter is not touched.
