The author's checklist: four places it could live

The Workflow area took over a local draft's Status drawer and turned it into a wall of paragraphs, one for every action. The owner rejected it, then widened the question from the drawer to authoring as a whole.

“What the heck happend to my status drawer?”

“I mean if we don't need status tab then we don't need it here. If there's information that isn't relevant we don't need to keep it. This looks to be the PR Authoring workflow so make sure whatever we design works for a Local PR, an existing Draft PR that we own, and a live PR we need to make revisions to.”

Mockups only. No product code changed. Every frame is drawn in the application's dark and light themes; the content is invented, and the workflow is the repository's synthetic organization fixture.

What the four options share

  • One checklist, three handoffs. An author's window answers one question: what is left before I hand this over? For a local draft the handoff is Create Draft PR…, for a draft pull request it is Ready for review, and for an open pull request that came back from review it is Publish response…. The handoff is one button at the right end of the review bar, where Submit review sits for a reviewer.
  • A workflow adds rows, not a panel. Its actions are rows among the author's other steps, in the order of the workflow file. Without a workflow the list is shorter and one quiet control offers the workflow.
  • Who runs a row is said once. An agent action runs in BetterPullReview and wears the agent accent. A companion action is one you run in your own terminal: pressing Hand off shows the exact command with Copy. Each kind has one glyph and one tooltip; no row repeats the explanation.
  • Trust is in the mark. A filled mark means BetterPullReview saw it itself, on this computer or on GitHub. An outlined mark means a companion reported it, and the words say Reported. Nothing a companion returns is drawn filled.
  • Removed, in every option. What is sent (the Create Draft PR… sheet already shows it before anything is sent), My review (files read and comments in review are a reviewer's), the two truncated pickers and every per-action paragraph. People becomes one Reviewers row.

A, One list: the Status tab becomes the author's checklist

The drawer keeps one tab and it holds one list: a headline that says where the pull request stands, then every step in small groups. The workflow's actions are rows in Prepare. The workflow's name and revision sit in a quiet line at the foot, which is also where a draft without one offers it.

Gives
  • One place, always in view on Overview, that reads top to bottom as what is left.
  • The publisher choice sits on the publish steps it changes.
  • The same list grows from a local draft to a pull request under review; nothing is relearned.
  • Closest to what the drawer was: the publish steps are still there.
Costs
  • The drawer is 340 points wide, so an action takes two lines and a command is cut short in its field.
  • With a workflow and feedback the list reaches about 560 points and scrolls in a short window.
  • Showing a command moves the rows under it.
  • The Status tab is on Overview only, so the list is out of view in Review.

B, Workflow tab: Status as it is, and a second tab for the workflow

The smallest change. Status stays what the application shows today, less the parts an author does not use, and the workflow gets its own tab beside it. The tab's label counts what the workflow still needs, and Status gains one line that opens it.

Gives
  • Status is untouched by a workflow, whatever the workflow holds.
  • The workflow has a whole tab: room for the full name, the revision and a command.
  • Least to build: the rejected area moves to its own tab and is cut down to rows.
Costs
  • Two places to look. What is left is split by where it comes from, not by what to do next.
  • The publisher is chosen in one tab and changes the steps in the other.
  • A draft without a workflow still carries the tab, or the tab comes and goes.
  • Status keeps today's sections, which were made for a reviewer; the feedback rows of an open pull request have no home here.

C, Overview table: the checklist is a table over Files, and the Status tab goes

The checklist moves into Overview's main column as a table in the Files table's manner: Step, Run by, State and one button. The author's Overview has no Status tab at all. Run by says who acts in a word, so no glyph has to be learned, and a command fits on one line.

Gives
  • The most room: one line per step, and who runs it in plain words.
  • No Status tab for an author, and nothing kept that is not about authoring.
  • A table the application already has, beside the one the author reads next.
Costs
  • It pushes Files down by its own height: about 200 points for a local draft with a workflow, about 330 for an open pull request.
  • Overview only, like A.
  • The description and the list of what is left compete for the top of the page.
  • Showing a command grows its row and moves the rows under it.

D, Header popover: the handoff's status is a button

The status beside the handoff button becomes a button itself. It says what is left in a few words and opens the checklist as a popover. There is no Status tab, the window's layout does not change, and the status is in view on every tab.

Gives
  • In view from Overview, Review, Discuss and Threads; the others are Overview only.
  • Nothing in the window moves, and Overview's whole width goes to the description and Files.
  • The status and the handoff are side by side, so the button's state is explained where it is.
Costs
  • Closed, it shows a few words. Which step is waiting takes a press.
  • A handoff is copy the command, run it in a terminal, come back and read the answer. A popover closes when the application loses focus, so the author reopens it to finish.
  • A tall popover over an open pull request covers the code it is about.
  • Ready for review moves from the title's line to the bar.

What the application lacks today

  • A workflow belongs to a local draft. A pull request that never had one has no workflow rows until a worktree is associated with it, which RFC-BPR-0122 proposes and nothing builds yet.
  • The feedback rows are proposed, not built. Address feedback (RFC-BPR-0122), the agent's evaluation and replies (RFC-BPR-0123) and Publish response… with its re-request (RFC-BPR-0124) are Proposed. Today the author has Threads, reply drafts, Resolve and Request review.
  • Since a reviewer's review is the reviewer's question today. RFC-BPR-0116 answers it for the person who reviewed. The author's row needs the same comparison from the other side.
  • The author sees a reviewer's drawer. Overview shows My review to the person who opened the pull request.
  • Ready for review ends the title's line (BPR-1852). Every option moves or repeats it at the right end of the review bar.

Recommendation

A, One list, keeping the status words beside the handoff button that the accepted local-draft design already has.

It answers both of the owner's remarks. The drawer shows status again, and only an author's status: the publish steps stay, the reviewer's sections go. It is the only option where the publisher sits on the steps it changes, and the same list serves a local draft, a draft pull request and a pull request sent back, growing a group at a time. Its cost is width. If the two-line rows read as cramped in the look, C is the same list with room, at the price of pushing Files down.
