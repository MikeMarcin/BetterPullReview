Rules every surface keeps

These are unchanged from round v1 except for the two rows marked v2.

Counting unitOne conversation (a native thread, a top-level comment or a review summary) counts once, classified by its root. Replies carry their own marks but never add to a count.
Other (catchall)The speech bubble in the Comments cell is Other as soon as any label has a chip: plain comments, labels without a chip, custom labels and unreadable roots. With no label chips chosen it counts everything. Chips + Other = the included conversations, in every scope. HairStrandsLighting.cpp is the pack fixture's src/cache.cpp: Open gives issue 2, question 1, Other 4 of 7. All gives issue 4, question 1, Other 5 of 10.
Not on a fileA last row holds unanchored threads, PR-level comments and review summaries.
ResolutionFour round state marks: open, resolved, unknown, not resolvable. Open is the default count. All puts a small state bar under each number. Unknown and not resolvable are never shown as resolved or as a clean zero. The ? chip lists what Open leaves out.
Labels vs states (v2)Labels are square and states are round. A label's tint fills its square softly and draws its border. The two letters stay in the ink colour, so contrast never depends on the tint, and the mark still reads in grey or with the tint set to the background. No default tint uses the amber of open or the green of resolved.
Identification (v2)Every mark has a tooltip and an accessible name with the label's word and any decoration, for example "issue (blocking)". The Label key (⌥K) shows all twelve tinted marks with their names and shortcodes.
Public vs localA label is public text at the start of the comment. The preview shows exactly what GitHub gets, which is plain text with no mark (v2 removes the mark round v1 drew in the preview). Copy source keeps the prefix. A shortcode is never sent: it becomes the label in the editor before anything is saved. Private defects keep their dashed, locked badge.
Native reviewComment, Approve and Request changes remain explicit. No label resolves, approves or requests changes.
SuggestionsA suggested-change block keeps its own header. A tick (or ↗ Apply on GitHub) appears only where GitHub can apply it.

2. Writing a labelled comment: the chip (A) and :shortcodes:

The label chip and its ⌘L menu are unchanged from round v1 except that each menu entry now shows its shortcode. Typing is the shortcut. A label's code is its mark's two letters between colons, so learning one teaches the other.

LabelCodeLabelCodeLabelCode
praise:pr:nitpick:ni:suggestion:su:
issue:is:todo:td:question:qu:
thought:th:chore:ch:note:no:
typo:ty:polish:po:quibble:qb:
WhereOnly at the very start of the comment, the place a label can go. Typed anywhere else, colons are plain text: FMath::Max, times and GitHub's own :emoji: codes are never touched.
CompletionA colon followed by one letter opens a list under the text. It lists every label whose code or name starts with what follows the colon, codes first. :q lists question and quibble; :qui lists quibble. Each row shows the tinted mark, the code, the name and its meaning. ↑ and ↓ move through the list, and Tab or Enter replaces the text with the highlighted label.
ReplacementTyping the closing colon of an exact code replaces it at once, without the list. :qu: becomes question: with the caret after it, in one undoable step. The chip shows the new label and offers its decorations. A small note says what happened, and ⌘Z right after puts back the literal :qu:.
Existing labelA code typed in front of an existing label replaces that label in the same step. A code never adds a second prefix.
DecorationsNot part of the codes. They come from the chip, from the menu, or from typing them.
Left as textEsc closes the list and keeps what you typed. A code that matches nothing (:zz:) stays as text. Pasted text is never replaced.
Helper offShortcodes belong to the label helper (Settings › Reviews & queue, off by default, accepted in round v1). With it off, :qu: is plain text. A label typed out in full (question: ) counts either way.

3. Labels on thread cards, v2

Round v1 drew the mark and the word together, which was rejected. In v2 a card's header holds only the root's mark, then the line, then the round state pill. A reply's mark sits in its name row, before the author. The word and any decoration appear only in the mark's tooltip and accessible name, for example "issue (blocking)". A plain comment and a plain tour stop show no mark. Copy source still keeps the prefix.

Alignment. Round v1 set reply marks inline in the text and pushed them 3 px down (vertical-align:-3px). That is why they looked low. In v2 every mark sits in a flex row with the text beside it, and both are centred on the same line. The frames measure this. With ?check=align, every mark's centre is compared with the centre of the text beside it. In th-wide, th-narrow and th-detail, in light and dark, the largest gap is 0.008 px across 6, 6 and 3 marks. The 200 % detail frame draws a dashed guide through each mark's centre.

5. Settings: Comment labels, and mark tints in Appearance

The Comment labels section in Reviews & queue was accepted in round v1. With B chosen, "Overview columns" becomes Overview chips, and the preview of A's header is gone. A new Mark colours row links to Appearance with its filter set to "label".

The tints follow the per-theme colour model accepted in RFC-BPR-0034. Each label is a colour role, "Label issue" and so on, in a fifth group, Comment labels, of the Colours card. The card then offers 57 roles instead of 45. Every theme variant (light, dark, high-contrast light and high-contrast dark) has its own built-in tint for each label. An edit applies only to the theme on screen and previews in the review window through the existing bar ("Previewing 1 colour change to Light…", Cancel or Keep changes). Import, Export and Reset all cover the tints like any other role, and a theme's customised count includes them. A stored palette that has no label roles reads them as the built-in tints, so existing customisations keep working without a change.

LabelLightDarkHigh-contrast lightHigh-contrast dark

The defaults are spread across the hue wheel and leave out the amber and green that states use. Their contrast with their own fill is not a concern, because the letters are always ink. BPR-1080 may still adjust them next to its icons.
