Discuss tab: collapsed cards and the full-screen column

The owner's two complaints, where each comes from in the code, and three designs. Each image is a link to the full-size PNG; light above, dark below.

Findings

1. A collapsed card prints the comment's Markdown source as one run-on line

display_of() (src/adapters/qt/src/conversation_cards_view.cpp:316) builds the closed note's text. It replaces every newline with a space (line 320), sets a recognised Conventional Comments header in semibold, and puts text between a pair of backticks in the code font. Nothing else is read: heading marks, list numbers, **, > quote marks, table pipes, ![…](…) image syntax and raw HTML are drawn as written. At the first code fence the loop meets two adjacent backticks and appends the rest of the body untouched (the close == open + 1 branch). measure_closed() (line 2735) gives the note two lines, or one when resolved, and clamp_lines() (line 363) elides the last line wherever the width ends, mid-syntax or not. The open card is a different path, markdown_body_view, and is not affected.

2. Nothing bounds the width, so a wide window multiplies the run-on

place_timeline() (src/adapters/qt/src/conversation_cards_view.cpp:2521) sets every row to the viewport's width less 16 points; there is no maximum anywhere in the view or in github_conversation_panel.cpp. The line count stays at two, so the amount of flattened source grows with the window: roughly 360 characters of it at 1280, 500 at 1728 and 740 at 2560. The replies, new count and resolved check are painted from the right edge (closed_meta()), which at 2560 puts them some 2,400 points from where the words start.

These three are reconstructions from the painting code, with a busier scenario than any fixture holds (31 comments, 17 threads, 6 from bots). No built executable renders Discuss at an arbitrary size, so the real render below is the calibration: today's build, offscreen, the busiest committed fixture with written conversations (tests/fixtures/github/pull-requests/conversations-v1, pull request 418, 24 threads) at the 1280 × 900 its test fixes. large-review-v1 holds 1,000 comments, but they are identical synthetic benchmark rows. Offscreen renders use Fusion and the light palette only.

3. Each thread repeats what the rows around it already said

  • Every thread gets its own full path:line row (src/adapters/qt/src/conversation_cards_view.cpp:2579), so four threads on one file print the same 50-character path four times.
  • A review is named on its bundle line and again on each note under it; the date appears only on the bundle line (d MMM yyyy, line 2528), so a comment outside a review shows no time at all.

4. The defaults are not the cause

  • Discuss has two filters, Only new and Hide resolved, both off until chosen and then remembered per profile (src/core/include/bpr/core/view_filter_memory.hpp, view_filter_choice). Resolved threads show dimmed on one line.
  • Discuss lists three kinds of thing: pull request comments, review summaries and inline threads (src/core/include/bpr/core/conversation_timeline.hpp, timeline_item_kind). Commits, force-pushes, labels, review requests and checks are not read for it and never appear, so there is nothing of that sort to turn off.
  • A bot is an ordinary author. Its report is the worst case of finding 1: a Markdown table flattened into pipes.

Defined by RFC-BPR-0028 (the Discuss modality), RFC-BPR-0085 (one card anatomy: "a flat closed note … two lines"), and cards BPR-0649, BPR-1290, BPR-1337 (header), BPR-1471 (right-hand column), BPR-1779 (comments, not review containers), BPR-1844 (remembered filters).

Options

A. Clean rows in a column (recommended)

Answers both complaints and changes nothing else. Every comment is still listed, the filters and their defaults stay as they are, and the open card is untouched.

  • The closed card shows the comment's first paragraph as words, and names what is not words with one quiet token each.
  • The list is a centred column 820 points wide at any window size; the header's chips and counts share its edges.
  • Replies, new count and resolved check each keep a fixed slot at the column's right edge, beside the words.
  • A file is named once, above its threads; each thread carries its line number. A review's summary row carries the verdict and date, so the separate bundle line goes. Every row has a date or a line.

The whole scenario takes 2.5 screens at 1280 × 800 against 3.7 today, with no row hidden.

B. A, with resolved threads and bot comments folded

The same rows. Runs of bot comments fold to one row, and a file's resolved threads fold into a count on its header. One Folded menu chooses what folds. This changes what a reviewer sees by default, which is why it is separate.

1.7 screens at 1280 × 800.

C. B, grouped by push

Each push becomes a heading with its activity summed on one line; under it only what is unresolved or new, and the rest in one fold. This is the only option that brings commits and labels into Discuss, and it needs data the application does not read today.

1.4 screens at 1280 × 800. The Folded menu, shown open on C (dark); B's has the first two items.

The collapsed preview, exactly

  1. Keep the Conventional Comments header in semibold, as today.
  2. Show the first paragraph of words. A body that opens with a heading shows the heading in semibold, then the first paragraph. A body that opens with a list shows its first item.
  3. Drop emphasis and link marks and keep their words. Inline code keeps the code font, as today.
  4. Name each block that is not words with one token, once per kind, in the order they occur: List, Quote, Image, Table, Details, Suggestion, or the code's language. A quote that comes before any words puts its token first, so a reply reads as a reply.
  5. Two lines, one when resolved, as today. End with an ellipsis only when words were left out, at a word boundary and never inside inline code. Tokens are never cut; the words give way to them.

Recommendation

Build A. It fixes the two things the owner named, at their source: one function decides what a closed card prints, and one width decides how far a row runs. It keeps the card anatomy RFC-BPR-0085 settled and the filters BPR-1844 remembers. B's folding is a small step on top once A is accepted, if a busy pull request still reads as too long. C waits on a decision to bring activity into Discuss at all.

Open questions

  1. Is 820 points the right column, and should it be centred or held to the left? The open card would take the same width.
  2. Should the open card be allowed wider than the column, for code blocks and suggested changes?
  3. Does a thread under a review still need its author's name and avatar? A drops them, since the review's row names the reviewer. Replies by others still show as faces.
  4. Tokens as words (List, Quote, C++) or as glyphs with tooltips?
  5. Should Review's Comments drawer and Overview's Comments use the same preview? They draw closed notes through the same function, so they would by default.
  6. For B: does folding replace Hide resolved, or stay beside it as drawn?
